# 数字读法（110 读幺幺零 还是 一百一十）

> 2026-09-28。结论先行：**「110 元读成幺幺零」这个问题不会发生**——文本前端本来就在
> 做语境判断。真正要补的缺口是**长号码**，见第四节。
> 本模块默认**关闭**（`NUM_NORMALIZE=1` 启用）。

## 一、谁在做这件事：三层链路

| 环节 | 实现 | 我们能否控制 |
|---|---|---|
| 自建引擎（Linux） | `indextts/utils/front.py` → `tn.chinese.normalizer`（WeTextProcessing + pynini） | 能改源码，但改动随镜像走 |
| 本地 mac 复现 | 同文件走 `wetext.Normalizer`（WeTextProcessing 的 C++ 移植） | — |
| 云引擎（302.ai / SiliconFlow / autodl.art） | 服务端实现，**未知** | ❌ 控制不了 |
| **本项目 backend** | `app/number_norm.py`（合成前预处理，本文件所述） | ✅ 全引擎通吃 |

前三层是「模型侧 TN」，第四层是我们的兜底。**TN 本身能力不弱**（见下），
所以我们的策略是**只补缺口、不抢活**。

## 四、本模块做什么

`app/number_norm.py`，只做**号码方向**（数字 → 逐位汉字），判定顺序：

```
候选：≥4 位连续数字，或带 - 分隔的号码形态

① 否决：后跟单位/量词（元/个/点/月/号/分/公里/%…）→ 交回 TN
② 否决：前面是幅度词（第/共/金额/股价/余额/体脂率…）→ 交回 TN
③ 否决：小数、日期（2026-09-28）、两段年份区间（2020-2024）→ 交回 TN
④ 命中：前 24 字或后 8 字的窗口内出现号码语境词
        （单号/订单/账号/卡号/身份证/手机/电话/座机/传真/分机/热线/客服/
          快递/工号/学号/车牌/社保/医保/邮编/流水/QQ/微信/支付宝/拨打…）
⑤ 命中：11 位手机号形态（1[3-9]xxxxxxxxx）
⑥ 命中：带分隔符且（≥3 段 或 总位数≥10）
⑦ 其余：不猜，交回 TN

读法：逐位，1 读「幺」（可用 NUM_ONE_READ=yi 改成「一」）
```

**否决优先于命中**，所以「订单金额110」不会被「订单」带偏。

## 五、开关与落点

```bash
# .env（改后需重启 backend，config 仅在启动时读）
NUM_NORMALIZE=1        # 启用（默认 0=关闭）
# NUM_ONE_READ=yi      # 可选：号码里的 1 读「一」而非「幺」
```

落点在 `queue_worker._execute_task`，与术语表同一位置（**合成副本**，
不回写 `task["lines"]`）：

```python
synth_lines = apply_glossary(task["lines"], terms)        # 术语表（用户意志）
if name_punct.ENABLED:        # 人名中点归一
    synth_lines = name_punct.apply_name_separator_rules(synth_lines)
if year_norm.ENABLED:         # 年份逐位读
    synth_lines = year_norm.apply_year_rules(synth_lines)
if time_norm.ENABLED:         # 时间读法（2026-09-30 新增，默认开）
    synth_lines = time_norm.apply_time_rules(synth_lines)
if num_value_norm.ENABLED:    # 数值读法（2026-09-29 新增，默认开）
    synth_lines = num_value_norm.apply_value_rules(synth_lines)
if number_norm.ENABLED:       # 号码读法
    synth_lines = number_norm.apply_number_rules(synth_lines)
```

**顺序不能换**：术语表在前（用户意志优先）；`year_norm` 必须在数值层之前
（否则四位年份会被按数值读）；时间层紧跟年份层（两层命中集合不相交：年份规则
只认「数字+年」，时间规则只认「数字:两位数字」）；数值层必须在号码层之前
（两层命中集合不相交，先跑数值层能让「有单位」的数字从号码层手里被正确接走）。
详见第十节。

顺序是**术语表在前**：用户若在术语表里手写 `110 → 一百一十`，会先生效，
本模块看不到阿拉伯数字，不会覆盖用户意志。

**回滚**：删掉 `NUM_NORMALIZE=1` 即恢复原状（代码路径直接跳过）。

## 八、年份读法（2026-09-29 新增，独立模块 `app/year_norm.py`）

**不要把年份塞进本模块**：本模块默认关闭（`NUM_NORMALIZE=1` 才启用），且
`UNITS` 里含「年」—— `2011年` 在本模块的判定里是「后跟单位 ⇒ 数值语境」，会被
**明确否决并交回 TN**。年份走独立的 `app/year_norm.py`，**默认开启**。

### 为什么需要它：规则没丢，链路换了

这条年份规则**本来就有**，在 `tts-server/podcast_engine.py`
（`_YEAR_PATTERN` / `_replace_year` / `_normalize_reading_text`），由 `_sanitize_text()`
在**本地 GPU 引擎**链路上调用。而线上是 Docker + 云端引擎
（`TTS_ENGINE_PREFERRED` 指向 302.ai / autodl.art），`queue_worker._execute_task`
的注释写得很直白：

> 配音/播客模式：不进 tts-server 播客引擎，走引擎适配层在 backend 进程内合成

⇒ tts-server 的年份规则**完全不在链路上**。这就是「以前修好了、现在又坏了」的原因：
不是代码丢了，是链路换了，规则留在了被绕过的那一侧。

### 为什么不交给 TN：它对空格敏感

IndexTTS 自带 TN **有**年份规则，但要求数字与「年」**紧邻**。实测
（wetext 替身，2026-09-29）：

| 输入 | TN 输出 | |
|---|---|---|
| `2011年` | 二零一一年 | ✓ |
| `2011 年` | 两千零一十一 年 | ✗ 一个空格就退化 |
| `2011年3月11日` | 二零一一年三月十一日 | ✓ |
| `2011 年 3 月 11 日` | 两千零一十一 年 三月 十一日 | ✗ |
| `1550～1850年间` | 一千五百五十～一八五零年间 | ✗ 左端按数值读 |
| `公元850年` | 公元八百五十年 | ✗ 三位年份按数值读（该读「八五零年」） |
| `2011年度报告` | 二零一一年度报告 | ✓（「年度」不是反例，这就是正确读法） |

从网页 / 文档粘贴的文本**经常带空格**，不能指望 TN；更要紧的是云引擎的 TN 是
**服务端实现、我们控制不了**。所以本层直接输出汉字 —— 汉字对 TN 透明
（实测 `二零一一年` 进 TN 原样输出），结果与跑哪个引擎无关。

### 规则

```
1550～1850年间   → 一五五零到一八五零年间     两端逐位读，分隔符统一「到」
1550 ～ 1850 年间 → 一五五零到一八五零年间     （含半角 -、— 一并收敛成「到」）
在 2011 年发生的事 → 在 二零一一年发生的事      吞掉「数字↔年」之间的空格
公元850年        → 公元八五零年             三位年份（2026-09-29 起）
```

**为什么分隔符要换成「到」**：TN 能把 `1550-1850年` 处理成「到」，但前提是
数字还是数字；一旦我们先换成汉字（`一五五零-一八五零年`），那个 `-` 就没人管了。
统一成「到」语义明确、不会被误读。

**三位年份带语境否决**（2026-09-29）：四位几乎不可能是「时长」，三位不一样 ——
`850年` 既可能是公元 850 年，也可能是「距今 850 年」。判据是**紧邻数字之前的词**：

```
公元850年   → 公元八五零年    年份（含 公元前/句首裸写）
850 年      → 八五零年        三位也吃空格
850年代     → 八五零年代      「年代」不拦
距今850年   → 距今850年       时长 ⇒ 不碰，交回 TN 读「八百五十年」
历时/长达/已有/用了/持续/超过/不到/约/近/共/仅/只有/第 850年 → 同上
100-200年   → 100-200年       破折号前的三位跳过（双三位更像时长区间）
从850年到950年 → 从八五零年到九五零年   ★ 前面是「到」不是分隔符，两端都改
```

**只对三位生效**：四位在时长语境下也照样改（`距今2011年` 是病句，不值得为它
引分支），四位行为一个字节都没变。

**不碰**：两位数字（`30 年房贷`）、三位时长（`距今850年`）、数字间的三位
（`100-200年`）、双三位区间（`850～950年`，与时长区间字面无法区分）、
右端无「年」的 `2020-2024`（可能是减法）。

### 位数范围是单一真源（`MIN_DIGITS` / `MAX_DIGITS`）

```python
MIN_DIGITS = 3   # 逐位读的**最少位数**（不足此位不碰）
MAX_DIGITS = 4
```

正则由这两个常量拼出，`/api/version` 也报 `text_pipeline.year_norm_min_digits`，
部署自检对它有断言。**为什么必须报出来**：`year_norm_enabled` 是布尔开关，
「只有四位」的旧版与「三+四位」的新版**都报 `true`** —— 2026-09-29 线上因此出现
过一句很迷惑的现象：

```
2011 读对、1550～1850 读对，偏偏 公元850年 读成「八百五十」
```

这个**精确组合**只有「四位版」能产生，但当时 `/api/version` 里看不出差异，
只能去逐行读 git 史才定位到「部署没跟上」。规律：**开关量证明不了版本，
能证明版本的是取值域**（数字、枚举、指纹）。

### 开关与落点

```bash
YEAR_NORMALIZE=0      # .env，默认开启；改后需重启 backend
```

落点在 `queue_worker._execute_task`，顺序 **术语表 → 人名分隔号 → 年份 → 时间 →
数值 → 号码**，作用于**合成副本**，不回写 `task["lines"]`（任务详情与存档仍是用户原文）。

### 测试

```bash
cd webui-backend
python tests/test_year_norm.py    # 158 项，含「本层产出进 TN 必须原样输出」
```

第四部分是关键：它验证「修复前 TN 确实读错（基线）→ 修复后逐位读」，
光比较字符串相等不足以证明修好了。第五部分核对 `MIN_DIGITS` / `MAX_DIGITS`
与正则**实际接受的范围**一致（逐位长验证 1~5 位），防止常量与正则脱钩。

## 八·二、时间读法（2026-09-30 新增，独立模块 `app/time_norm.py`）

`12:30` → 十二点三十分、`9:05` → 九点零五分、`8:00` → 八点整。**默认开启**。

### 又是同一个故事：规则留在被绕过的那一侧

时间规则原本只在 `tts-server/podcast_engine.py`（`_replace_time`），而云引擎不经过
tts-server ⇒ 走 302.ai / SiliconFlow / autodl.art 时，`12:30` 以阿拉伯形态进模型。
与年份读法是同一个迁移故事（见第八节）。

### 实测：TN 大部分读得对，缺口是具体两类

用 wetext 替身实测（`lang='zh'`, `operator='tn'`）：

| 输入 | TN 输出 | 判定 |
|---|---|---|
| `12:30` | 十二点三十分 | ✓ |
| `会议定在12:30开始` | 会议定在十二点三十分开始 | ✓ |
| `下午 3:16 开会` | 下午 三点十六分开会 | ✓ |
| `8:00` | 八点 | ✓（少了「整」） |
| **`12 : 30`** | **十二比三十** | ✗ 冒号两侧带空格 ⇒ 退化成比例 |
| **`0:30`** | **零比三十** | ✗ 小时为 0 ⇒ 退化成比例 |
| **`0:00`** | **零比零零** | ✗ 同上 |

「带空格就退化」与 `year_norm` 撞的是同一个坑（`2011 年` → 两千零一十一 年）——
从网页/文档/PPT 粘贴的文本经常带空格。更要紧的是云端 TN 是**服务端实现**，
各厂商不同、我们既控制不了也测不到。

### 规则与边界

```python
_TIME_PATTERN = re.compile(r"(?<![\d:：])(\d{1,2})\s*[:：]\s*(\d{2})(?![\d:：])")
```

- 分钟**固定两位** ⇒ `3:2`（比分）、`16:9`（比例）、`1:2`（版本号）天然不命中。
- 两个否定环同时挡数字与冒号 ⇒ `123:45` / `12:345` / `12:30:45` / `1:12:30`
  整串不命中，**原样交回 TN**（TN 实测把 `12:30:45` 读成「十二点三十分四十五秒」）。
  只挡数字是不够的：那样 `12:30:45` 会被截成「十二点三十分:45」，留下一个孤立
  冒号 ⇒ 冒号仍可能被读成「比」。旧 tts-server 的正则正是这个毛病，本次一并修掉。
- 时/分越界（`99:99`）原样返回；`24:00` 不碰（「二十四点」是合法读法，交回 TN）。
- 读法：整点 → 「八点整」；分钟 <10 → 「九点零五分」（补零）；其余 → 「十二点三十分」。
  小时与分钟共用同一个 0~99 中文读法函数。

**已知取舍**：`3:16` 这类章节/经文引用会被读成「三点十六分」。**TN 也这么读**
（实测），所以不加左语境否决 —— 加了反而会让两条链路读法不一致。

### 必须与 tts-server 保持等价

音色**试听**（`routes/voices.py` → tts-server `/api/synthesize`）**不走**本链，
所以 tts-server 侧必须保留自己的时间规则；两处规则一旦不同，用户会听到
「试听对、正式合成不对」。两边刻意保持同一套读法，改动必须同步。
本次相对 tts-server 旧实现的行为变更是**分钟 ≥10 由逐位读（`三零`）改为规范读法
（`三十`）**，tts-server 侧已同步改（`podcast_engine._chinese_under_100`）。

### 开关、可观测与部署自检

- `TIME_NORMALIZE=0` 关闭（**默认开**；改 `.env` 后需重启 backend）。
- `/api/version` → `text_pipeline.time_norm_enabled` + **`time_norm_max_parts`**（=2，
  只做「时:分」；将来做「时:分:秒」会变 3）。报取值域而非只报开关 —— 理由同第八节。
- `tools/deploy_g1_autodl.sh` 两条路径都断言 `time_norm_max_parts >= 2`。
- `tools/diagnose_text.py` 的链路已从「六道关」改成**七道关**，中间态里有「时间」一行。

## 九、阿拉伯数字在**云端引擎**上读法不稳定（2026-09-29）

> **本节的初版结论是「数字与量词之间的空格让 TN 失效」，已被第二组实验推翻。**
> 保留这段修正记录 —— 「一个自洽的机制 + 一组支持它的数据」最容易骗过自己：
> 第一组数据（孤立短句）里 `230 倍` 逐位、`230倍` 数值，看着完美支持「空格」假说；
> 第二组换到同一语境，`汽车的 230倍`（**无空格**）照样逐位，假说当场崩塌。

### 现象

用户报：`美国自 2005 年至 2007 年的飞行安全度是汽车的 230 倍。`
—— 里面的 `230` 被读成了「二三零」。

**同一句里 `2005 年` / `2007 年` 却正常**，这个「为什么这个错、那个对」是关键线索。

### 直接机制：阿拉伯数字在 bpe 词表里根本不存在

```
"230倍"     -> ['▁', '230', '倍']              ← 230 是 <unk>(id=2)
"230 倍"    -> ['▁', '230', '▁', '倍']         ← 同样 unk
"两百三十倍" -> ['▁','两','百','三','十','倍']    ← 无 unk
"二三零倍"   -> ['▁','二','三','零','倍']         ← 无 unk
```

⇒ **数字只要以阿拉伯形态进模型，就落成一个 `<unk>`，模型在那个位置自由发挥。**
汉字则完全稳定。**这是唯一确凿的一环**（本地 bpe 实测）。

### 实测（autodl.art，各 3~4 次，同一音色；尺子 = 去静音有效时长）

| 送入文本 | 有效时长 | 判定 |
|---|---|---|
| `两百三十倍`（5 音节基准） | 0.85–0.99s | — |
| `二三零倍`（4 音节基准） | 0.74–0.79s | — |
| `230 倍`（孤立） | 0.76–0.79s | 逐位 |
| `230倍`（孤立） | 0.80–0.86s | **跨在两区间中间** |
| `汽车的两百三十倍`（基准） | 1.65–1.77s | — |
| `汽车的二三零倍`（基准） | 1.35–1.53s | — |
| `汽车的 230 倍` | 1.42–1.45s | 逐位 |
| **`汽车的 230倍`** | **1.45–1.46s** | **逐位（无空格也一样）** |

**两条要点**：
1. **「空格」不是决定性变量** —— 无空格的 `汽车的 230倍` 同样被逐位读。
2. **`230倍` 孤立时落在两区间正中** ⇒ 读法**本身就不稳定**：同一输入不同次
   可能念「两百三十」也可能念「二三零」。这与 skill `indextts-text-frontend-repro`
   里那条「`do_sample=True` 且无 seed，同参数两次调用读法可能不同」同源，
   区别在于这里连「念成几个字」都不固定。

**所以不稳定的不是写法，是「阿拉伯数字进了模型」这件事本身。**

### 为什么本地测不出来

`wetext`（mac）对 `230倍` 与 `230 倍` **都会**转成「两百三十」。
⇒ **本地 wetext 通过 ≠ 线上通过**。Linux 的 WeTextProcessing 版与 wetext 有差异；
云引擎（autodl.art / 302.ai）更是服务端实现 ——
**目前只能确认「这些数字没有被转成汉字」，无法确认其 TN 是不存在、还是规则不同。**

**推论（未实测）**：`110元` / `拨打110` / `快递单号1234567890` 这类**同样有风险** ——
只要数字以阿拉伯形态抵达模型就有风险，与有没有量词无关。
**上线前必须用一组「TN 经典样例」真机听一次**，才能判断云端 TN 到底在不在链路上。

### 客观判据：用「去静音有效时长」，不要用总时长

总时长含头尾静音、抖动 ±0.17s，会把「4 音节 vs 5 音节」这 0.13s 的差淹掉
（两组区间在 1.65s 处直接相接 ⇒ 按纪律只能记「不可判」）。去掉静音后基准才分离。

⚠️ 即便分离了也要看**间距 vs 基准自身跨度**：本次 context 组间距 0.12s、
而逐位基准自身跨度 0.18s ⇒ **样本 <5 次时不要用它下强结论**。

探针 `tools/probe_number_reading.py`：

```bash
python3 tools/probe_number_reading.py                  # 短句隔离变量（6 变体）
python3 tools/probe_number_reading.py --suite context   # 同语境「修复前 vs 修复后」
python3 tools/probe_number_reading.py --engine 302ai    # 换引擎对照
```

自动打印有效时长区间 + 逐变体判读（与两个基准的重叠情况），并生成试听页。

### 修法方向（比初版大）

初版以为「删空格」就够，实测否定了。真正的修法是**让数字以汉字形态进模型**：

- **A（推荐，切口可控）**：在 backend 把**数值语境的阿拉伯数字**转成汉字
  （后跟量词/单位、前有幅度词；位数 1~4 位）。复用 `number_norm.py` 已有的
  `UNITS` / `NUMERIC_PREFIXES` 表做**正向命中**，号码语境仍交回 TN。
- **B（最稳但最重）**：接管全部数字，自己实现「数值 → 汉字」，彻底不依赖 TN。
  规则量大（万/亿/小数/百分比/负号），但不再受云引擎行为影响。
- **C（不推荐）**：只提示用户别写阿拉伯数字 —— 治标不治本。

**落地前必须先补两个事实**：① 302.ai 是否同此规律；② 云端 TN 到底在不在链路上
（送一组 `110元` / `拨打110` / `快递单号1234567890` 真机听）。

> **2026-09-29 已按 A 落地**，见第十节。范围由用户定为 v1：整数 / 小数 / 百分号 /
> 千分位；区间不做。

## 十、数值读法（2026-09-29 落地，独立模块 `app/num_value_norm.py`）

### 它解决什么

第九节的结论：**阿拉伯数字在云端引擎上读法不稳定**，因为 IndexTTS 的 bpe 词表
（12000）里根本没有阿拉伯数字 —— `"230倍"` 编码成 `['▁','230','倍']`，`230` 就是
`<unk>`(id=2)，模型只能自由发挥。而云端 TN 不可依赖（`230 倍` 原样进了模型）。

⇒ 修法就是**让数字以汉字形态进模型**。这一层负责「数值语境」的那一半。

### 与号码层是正交互补的两面（这是方案能收敛的关键）

| | 号码层 `number_norm.py` | 数值层 `num_value_norm.py` |
|---|---|---|
| 前提 | **没有**单位、**没有**幅度词 | **必须有**单位或幅度词 |
| 判定 | 号码语境词 / 手机形态 / 带分隔号码 | 右邻单位、左邻幅度词、紧跟 `%` |
| 动作 | 逐位读（幺幺零） | 数值读（一百一十） |

号码层的第①②条否决条件，正好是数值层的命中条件；两层的左语境窗口用的还是**同一个
函数**（`number_norm._context_before`，刻意不复制）。所以两层在**同一段文本上的命中
集合交集恒为空**、并集覆盖「有明确语境」的全部数字。

`tests/test_num_value_norm.py` 第 5 部分把这条性质写成了断言（28 句语料，无一句被
两层同时命中）—— 它一破就意味着出现了重复替换、或两边都撒手。

### 判定顺序（否决优先，永不猜）

1. **形态**：`(?<![0-9A-Za-z.,])` 起、`(?![0-9])` 止 ⇒ `v2.0` / `SN12345` / `A4` 出局。
2. **位数**：整数部分 > `MAX_DIGITS`(8) 直接放行。
   ⚠️ 这道必须有：`_read_int` 只按「万」分段，位数超了会把高位**静默丢掉**
   （`999999999` 会读成 99999999，差一个数量级），比不处理糟。
3. **否决**：两侧出现 `- – — － ~ ～ / : . ,` 且另一侧还是数字 ⇒ 不是数值语境。
   这一条同时挡住日期 `2026-09-28`、时间 `3:30`、区间 `100-200`、版本 `1.5.2`、
   带分隔号码 `400-123-4567`。**「数字 空格 数字」同样否决**（`1 234元` 是写坏了的
   千分位，TN 对它也只读对一半）。
4. **命中**：右邻（跳过空格）是单位/量词，或左语境窗口末尾是幅度词，或紧跟 `%`/`％`。
5. 其余原样保留，交回 TN。

### 转换规则与「两/二」

`tests/test_num_value_norm.py` 第 3 部分有一张 **wetext 基准表**（`110元`→一百一十元、
`105`→一百零五、`1200米`→一千二百米、`2000次`→两千次、`30%`→百分之三十…），
本层输出与之逐字比对 —— 自己实现「数值→汉字」最容易跑偏的不是算法，是**读法习惯**。

**但「两」刻意不复刻 TN**：TN 自带 lexicon，`2元/2个/2米`→两、`2倍/2年/2月/2号`→二，
按词不按位。本层用一套自洽规则：

- 最高段最高位是 2 且落在百/千位 ⇒ 两（`200`→两百、`2000`→两千、`2200`→两千二百）
- 独立的一个 2 ⇒ 两（`2元`→两元、`第2名`→第两名）
- 其余一律二（`20`→二十、`1200`→一千二百、`2200**0**`→两万二千，不是「两万两千」）

比对时做 **「两 ≡ 二」等价化**，否则会假失败。

刻意不一致的只有三处，每处都有理由（测试里逐条打印）：
`30％`（TN 不管全角，本层管）、`涨了110点`（TN 读幺幺零点，本层读一百一十点）、
单个 2 的 两/二。

### 与 `year_norm` / `time_norm` 的顺序耦合

顺序固定：`glossary → name_punct → year_norm → time_norm → 数值层 → 号码层`。

- `2011年` / `公元850年` 由 `year_norm` **先**换掉，本层看不到；
- `12:30` 由 `time_norm` **先**换成汉字 —— 本层本来也把「两侧都是数字的分隔符」
  （含 `:`）列为否决，两层不争抢；先换掉之后本层连那串阿拉伯数字都看不见了；
- `year_norm` 刻意**否决**的形态（`距今850年` 这类时长）落到本层，由「年」命中
  ⇒ 读「八百五十年」—— 正是时长该有的读法。两层在此天然接续，不必再加词表。
- 本层对**四位数字紧邻「年」**另有一道否决兜底（万一 `YEAR_NORMALIZE=0`，
  宁可交回 TN，也别读成「两千零一十一年」）。

### 开关、可观测与部署自检

- `NUM_VALUE_NORMALIZE=0` 关闭（**默认开**，用户 2026-09-29 定）。
- `/api/version` → `text_pipeline.num_value_normalize` + **`num_value_max_digits`**。
  报取值域而不只报开关 —— 这是第九节第九条教训的直接应用：布尔开关证明不了版本。
- `tools/deploy_g1_autodl.sh` 两条路径都断言 `num_value_max_digits >= 8`。
- `tools/diagnose_text.py` 已把链路改成**七道关**，中间态里有「时间」「数值」各行：

  ```
  原文   : 会议定在 12 : 30 开始，2011 年 230 倍的量
  年份   : 会议定在 12 : 30 开始，二零一一年 230 倍的量
  时间   : 会议定在 十二点三十分 开始，二零一一年 230 倍的量
  数值   : 会议定在 十二点三十分 开始，二零一一年 两百三十倍的量
  ```
