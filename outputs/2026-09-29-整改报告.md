## 二、实际改动与架构链路

### 2.1 合成链路

队列 → queue_worker → mono_runner / podcast_runner → select_engine → 进程级 EnginePoolFacade → 段级全局租约 → 独立资源适配器 → 音频规范化 → 播客既有变速/响度处理（仅 podcast）→ 按原文本顺序拼接 → outputs 落盘。

池不是每个任务重建的对象：所有任务共享每资源 inflight、健康 TTL、冷却、音色缓存。runner 并发信号量仅控制任务内部；实际资源上限由池租约控制。没有扩展数据库，没有引入多 worker 协调。

相关改动：app/engines/base.py、factory.py、selector.py、indextts_art.py、__init__.py、mono_runner.py、podcast_runner.py；新增资源池测试并修改注册语义测试。

### 2.2 签到 20 积分

根因：service.py 的 CHECKIN_BONUS 缺省值原为 5，示例/文档也为 5；只改缺省值不能覆盖部署机器已有 .env 中的旧值。

实际 diff：默认值改为 20，.env.example 与 MEMBERSHIP.md 同步；compose 显式传 MEMBER_CHECKIN_BONUS=${MEMBER_CHECKIN_BONUS:-20}，进程环境优先于挂载的 backend .env。部署环境仍可设其他金额或 0 关闭。非 Docker 启动时，已有显式 MEMBER_CHECKIN_BONUS=5 会继续覆盖缺省值，需要部署方自行决定是否更新。

既有风险：checkin 先 load_checkins、检查日期、save_checkins，再 _apply_delta；不是跨签到记录和积分流水的原子事务。并发请求可能竞态，崩溃可能出现已记签到但积分未落账。此次只调整金额与覆盖入口，未宣称解决原子性；未来需事务或覆盖完整操作的锁和幂等键，并验证崩溃恢复。

### 2.3 下载名称

根因：前端 download 属性提示项目名，但后端 Content-Disposition 仍传 mono_<id>.wav / podcast_<id>.wav，浏览器实际保存名受响应头影响；播客还存在重复路径注册，修改一条路由不能保证实际命中。

实际 diff：queue_state.audio_download_name 统一项目名称清理、Windows 保留名、控制字符、重复 .wav 后缀和 UTF-8 长度限制；mono 本地 FileResponse 与 podcast 本地/历史代理响应使用统一名称；移除 mono.py 中重复 podcast audio 路由；历史 tts_task_id 增加映射；前端 helper 同步后端规则。磁盘 output_path 不改，旧任务无项目名保留旧式回退名。

既有安全风险：音频路由仍不按用户归属鉴权。随机 task_id 不是授权机制，拿到 URL 的人可能访问音频；历史代理路径也需单独评估。此次不能为修下载名而贸然添加 Authorization 要求，否则原生 audio 标签播放可能断裂。未来应设计短时签名 URL 或兼容播放的 cookie 授权，并一起验证播放、Range、下载、过期和任务所有权。

## 三、池调度、探测与计费边界

1. local 强制 tier=local 和 max_concurrency=1；本地空闲优先，满载云端溢出。
2. 云端排序为 inflight/capacity/weight；平局使用累计分配段数/weight，避免顺序小任务永远首账号。权重按段数公平，不是按文本长度、GPU 时间或费用公平。
3. 非付费只读 health 默认 TTL 15 秒，同资源共享探测任务，上限 12 秒。探测证实连通/鉴权，不等于余额充足或模型一定可用。
4. art 无已确认免费 probe，明确 unverified；真实业务请求才验证，不额外发付费试音。
5. 探测或真实调用失败隔离资源 120 秒；到期后业务触发重新探测，无后台付费轮询。全部隔离立即报错，不越过冷却。
6. 普通满载等待不计故障；pool 整体 mark_failed 被忽略。
7. 进入适配器后的异常保守包装 NonRetryableSynthesisError，mono/podcast 均不自动重提该段。未知提交超时、轮询失败、音频取得失败、转码失败均不跨资源补发。302.ai 原有连接未建立重试、GET 轮询行为保留。
8. 账号缓存按资源 id + provider/endpoint/凭据指纹隔离；换 key 不复用旧账号 URI。首次使用新隔离缓存可能重新上传参考音频并产生平台原有上传费用。
9. 未设置 TTS_RESOURCES/TTS_RESOURCES_FILE 时旧 env 自动转成池，无需迁移配置。TTS_ENGINE_PREFERRED 弃用告警，不保留旧“优先级锁任务”算法。

### 取消行为的准确说明

UI 取消调用设置 cancel_requested=true，提示"正在取消，等待进行中的合成结束"。runner 在进入 worker 时检查标记，gather 等待已经进入调用的段完成后把任务设为 cancelled。

**本轮补充（提交前取消）**：SegmentRequest 新增可选 `should_cancel` 钩子，两个 runner 都传入 `lambda: bool(task.get("cancel_requested"))`。资源池在三个点位检查它：①等待租约的循环开头；②拿到租约但在提交前；③等待时用 0.5s 超时轮询唤醒。命中即抛 `SynthesisCancelled`，该段**从未提交给平台**，因此不产生费用，也不隔离资源（与 asyncio.CancelledError 区分）。两个 runner 的重试逻辑同样排除该异常。

因此现在的取消语义分两层：
- **排队中/尚未提交的段** → 立即放弃，零费用（本轮新增，已有专项测试）；
- **已经提交给平台、正在轮询或已经进入适配器的段** → 只是本地不再等待，远端平台任务**可能继续执行并计费**。

第二层是本轮未解决的边界：协程被真正 CancelledError 取消时，池 finally 释放租约并隔离该资源一段时间，但不会调用平台取消接口。要彻底解决需要按平台协议实现远端取消/状态确认。不要把本轮的测试结果写成"UI 可以立即取消远端任务"。

## 四、音频规范化与独立 review 结论

池先统一输出 24kHz、mono、PCM16 WAV，然后 podcast 才执行 _normalize_segment。因此 podcast ffmpeg 不存在或失败时返回的原始输入已经规范化，不会重新产生采样率不一致。本轮专项测试从 22050Hz 双声道 PCM8 转换到统一格式，模拟 podcast 无 ffmpeg 回退后执行 _concat_wavs，验证通过；未盲改既有回退。

**本轮修正（规范化优先级）**：原实现先用标准库线性插值，只在 wav 解析失败时才找 ffmpeg —— 等于只要音频是合法 wav 就永远绕过 ffmpeg，装了也用不上，且线性插值没有抗混叠滤波。现改为：①已是目标格式（24k/mono/PCM16）→ 零转换直接返回；②有 ffmpeg → 交给 ffmpeg 重采样（带抗混叠，音质最好）；③无 ffmpeg 或 ffmpeg 失败 → 标准库线性插值兜底并**明确记 warning**。同时 ffmpeg 定位不再只查 PATH，改为与 podcast 路径一致的 PATH + 常见安装路径兜底（本机 ffmpeg 在 /opt/homebrew/bin 但不在 PATH，旧写法会误判"没有 ffmpeg"）。`fix_wav_header` 上收到 engines.base，podcast_runner 的同名函数改为薄封装，删除重复实现。

整数 PCM 使用标准库解码、声道平均和线性插值；其他编码需 ffmpeg。线性插值不是高品质抗混叠重采样，需真实听感验收。池规范化不解决不同模型的音色和情绪差异。

**已核实的既有缺陷（本次刻意未修，按要求只报告）**：Speed 在播客路径上可能被应用两次。证据链——`indextts_local.py:72` 与 `indextts_siliconflow.py` 都把 speed 传给了服务端（两者 `supports_speed=True`），而 `podcast_runner._normalize_segment` 在 `abs(speed-1.0)>=0.001` 时**无条件**再套一次 `atempo`，未参考 `capabilities.supports_speed`。即：播客 + 本地/SiliconFlow 引擎 + speed≠1 时，实际语速约等于 speed²。该逻辑不是本分支引入（`git diff` 确认 `_normalize_segment` 未改），是引擎层迁移时留下的。修法很小（仅当 `not caps.supports_speed` 时才加 atempo），但会改变现网播客听感，故留给老哥决策后再动。混池时更复杂：池的能力是各资源的「与」，若某段实际由支持 speed 的本地节点承接，仍会二次变速。

## 四之二、本轮第二轮修复（提交前取消 + 规范化优先级）

- `SegmentRequest.should_cancel`：见第三节取消行为说明。两个 runner 均传入，池在等待/提交前检查，0.5s 超时轮询保证排队中的段也能及时退出。
- `SynthesisCancelled`：新增异常类型，语义为"提交前主动放弃"。资源池不隔离资源，runner 不重试，取消检查走原有 cancelled 分支。
- `normalize_pcm`：改为 ffmpeg 优先 + 格式快速通道 + 标准库兜底（含 warning）。
- `find_ffmpeg` / `fix_wav_header`：上收到 engines.base，podcast_runner 复用，消除重复实现。

## 五、完整资源配置与 Docker 接入

### 5.1 无密钥 JSON 示例

推荐文件 webui-backend/data/config/tts-resources.json：

```json
[
  {"id":"gpu-a","provider":"local","base_url":"http://tts-a:8000","max_concurrency":1,"weight":1,"tier":"local","shared_voice_paths":true},
  {"id":"gpu-b","provider":"local","base_url":"http://tts-b:8000","max_concurrency":1,"weight":1,"tier":"local","shared_voice_paths":true},
  {"id":"account-a","provider":"302ai","api_key_env":"TTS_302_ACCOUNT_A","max_concurrency":2,"weight":1,"tier":"cloud"},
  {"id":"account-b","provider":"302ai","api_key_env":"TTS_302_ACCOUNT_B","max_concurrency":4,"weight":2,"tier":"cloud"},
  {"id":"sf-a","provider":"siliconflow","api_key_env":"TTS_SF_ACCOUNT_A","max_concurrency":2,"weight":1,"tier":"cloud"},
  {"id":"art-a","provider":"art","api_key_env":"TTS_ART_ACCOUNT_A","max_concurrency":2,"weight":1,"tier":"cloud"}
]
```

tts-a/tts-b 是部署方需自行提供的服务名，不是已部署节点。不能把容器内 127.0.0.1 当宿主机 GPU 服务。不能把同一物理 GPU 或同一账号用多个 id 重复配置来虚增容量。

backend .env 中设置以下变量名；下方尖括号仅占位，不是真实凭据，不可原样用于生产：

```dotenv
TTS_RESOURCES_FILE=/app/data/config/tts-resources.json
TTS_302_ACCOUNT_A=<由部署方安全填写账号A密钥>
TTS_302_ACCOUNT_B=<由部署方安全填写账号B密钥>
TTS_SF_ACCOUNT_A=<由部署方安全填写SF密钥>
TTS_ART_ACCOUNT_A=<由部署方安全填写ART令牌>
```

也可将完整 JSON 压成单行写 TTS_RESOURCES；它优先于 TTS_RESOURCES_FILE。不要同时保留旧的内联列表并期望文件覆盖。空列表/无效 JSON/重复 id/缺凭据失败，不静默回退。只使用旧 env 时不必新增任何上述变量。

### 5.2 Docker 挂载方案

现有 compose 已挂 ./webui-backend/data:/app/data 与 ./webui-backend/.env:/app/.env:ro；本轮复用已有数据卷放非敏感 JSON，不新增可能导致缺文件部署失败的强制挂载。compose 添加说明，factory 新增 TTS_RESOURCES_FILE 读取入口。

密钥只由现有 backend .env 加载，不写 compose environment，不烘焙镜像，不将真实 .env/凭据复制到 outputs。部署方限制 .env 文件权限，避免打印环境、docker inspect 或 docker compose config 中的敏感值。修改配置后需要重启；修改 compose environment 需重建容器，不能仅 restart 期待其更新。本次未执行任何容器操作。

### 5.3 多本地节点：部分实现

只有多个 URL 无法共享参考音频文件。当前 local /api/synthesize 接收服务器路径，没有新增上传接口；多 local 必须每个显式 shared_voice_paths=true，表示相同绝对路径对应同一参考音频。代码校验该声明，但不能证明远端文件真实存在。

**2026-09-29 用户决定：先用共享挂载**（同一存储域内 NFS / 目录挂载 / 同机多实例），不在同一存储域时由用户自行上传同步；**上传接口列为后续待办**（见第九节排期表 P2）。在此之前不要对外宣称「只填 URL 就能多机共用音色」。

### 5.4 默认 endpoint 和版本识别

专项构造测试确认省略 302.ai base_url 时真实适配器得到 https://api.302ai.com，不是空串、错误 provider 或拼接后的 /api 地址；适配器继续追加 /302/index_tts2/task。SiliconFlow 缺省沿用适配器默认国内站，旧 env 的 base URL 与 model 继续生效；art base_url 语义为服务根地址。

engine_summary 增加 pool_schema_version（本轮第三轮由 2 升到 3，配合语速契约）与 speed_guaranteed；resources 提供 id/provider/tier/max_concurrency/weight/inflight/in_cooldown/health/health_age_sec，不包含 key、endpoint、凭据指纹。schema 是结构版本信号，不是部署提交 SHA；判断线上是否新代码仍需版本信息配合，而本次没有线上验证。

## 十、第三轮：语速只在资源侧应用一次（本轮新增）

### 10.1 根因

「语速」此前有两个应用点，判据是 `EngineCapabilities.supports_speed`：

| 场景 | 引擎原生变速 | 播客层 atempo | 实际结果 |
| --- | --- | --- | --- |
| 本地 / SiliconFlow（原生支持） | 生效 | 无条件加 | **speed²**（调到 1.5 ≈ 2.25 倍） |
| 302.ai / autodl.art（无 speed 字段） | 不生效 | 加 | speed ✓ |
| 资源池（混池） | 按段决定 | 无条件加 | 原生那部分段 speed² ❌ |

池门面用 `all(c.supports_speed)` 声明能力，混池时是 False —— 播客层据此**对每一段**都加 atempo，而被选中的资源可能本来就是原生变速的，于是叠加。同一个能力字段在 mono 路径上方向相反：mono 从不做后处理，302.ai/autodl.art 的语速**静默丢失**（一直没人报，因为听感是「没变化」而不是「错了」）。

### 10.2 改法：把「谁应用语速」变成显式契约，并收敛到资源侧单点

- `EngineCapabilities` 新增 `speed_guaranteed`：True = `synthesize_segment()` 返回的音频**已经是** `req.speed` 的语速，调用方不得再变速。池门面恒为 True；单引擎适配器默认 False（诚实声明）。
- 池 `synthesize_segment()`：按**实际服务该段的资源**决定 —— 原生支持就把 speed 原样传给引擎（不改请求），否则在 `normalize_pcm(result, speed)` 里用 atempo 补齐，且与重采样合并进**同一次** ffmpeg 调用（不额外多跑一次 ffmpeg）。
- `normalize_pcm(data, speed=1.0)`：speed 的语义是「本层要补的语速」；speed=1.0 且已是目标格式时保持零转换快通道。
- 新增 `atempo_filters(speed)`：单个 atempo 只接受 0.5–2.0，超出自动串联（0.25× → `atempo=0.5,atempo=0.5`；4× → `atempo=2.0,atempo=2`）。替掉各处 `max(0.5, min(2.0, speed))` 的静默截断。
- `podcast_runner`：`_normalize_segment(data, speed)` 的 speed 改为「本层要补的语速」，任务开始时按 `caps.supports_speed or caps.speed_guaranteed` 决定传 1.0（生产路径恒为 1.0，只保留裸引擎兜底），并打一行「语速由哪一侧应用」的日志。
- `mono_runner`：不加后处理（语速由资源侧保证）；只有在「既非原生、也没有池保障」时打 warning，避免将来静默丢语速。

### 10.3 版本信号与部署自检

`pool_schema_version` 2 → 3，`engine_summary` 增加 `speed_guaranteed`；`tools/deploy_g1_autodl.sh` 在 **Docker 与裸进程两条自检路径**都断言 `pool_schema_version >= 3 且 speed_guaranteed is True`，并打印取值。为什么必须看取值域：混池时 `supports_speed` 新旧两版都报 False，开关量分辨不出来（与 `year_norm_min_digits` 同一教训）。

### 10.5 影响与限制

- **302.ai / autodl.art 在 mono 路径的语速以前被忽略，现在会生效** —— 这是修好一个静默失效，不是回归；如果你听到单人口播对这两家平台的语速有变化，原因在此。
- 播客里 speed≠1 的成品会**比之前慢**（回到你设定的语速）。你反馈的「加速听起来比较快」与根因一致。
- 限制：本地引擎的 `params.speed` 是否真被 tts-server 采纳未做联调（tts-server 线上不在链路）；无 ffmpeg 时非原生资源的语速不生效（会有 warning）；原生变速与 atempo 的音色细节不同，跨资源混用仍需听感验收。

### 10.6 P1：签到/兑换的并发原子性（本轮新增）

**根因**：`store` 的锁只保证单次读/写原子，保护不了「读文件 → 判断 → 写回 → 发积分」这段**跨读写的业务判断**。两个并发签到都能读到「今天未签到」，于是各发一次积分。优惠码兑换是同一类问题，且因优惠码是**跨用户共享**资源，还多一层「两个人同时兑同一个单次码」。

**改法**（只动 `app/membership/service.py`）：

- 新增 `user_lock(user_id)`：按用户互斥的**可重入**锁（`threading.RLock`）。`checkin()` 整段持有，`_apply_delta()` 也持有 ⇒ 同一用户的积分读改写不会互相覆盖，且 `checkin` 内部再调 `_apply_delta` 不会自锁。
- 新增进程级 `_redeem_lock`：串行化**跨用户**对同一优惠码的「读码 → 占坑 → 写回」。
- 锁顺序统一为 `_redeem_lock → user_lock → store._lock`，无反向路径，不会死锁。

**证据（不是「改完就通过」，而是对照证明）**：同一脚本里放一份修前实现做对照，8 线程 Barrier 对齐后同时签到：

| 版本 | 结果 |
| --- | --- |
| 修前（无锁） | 成功 **5** 次 / 409 3 次 ⇒ 余额 200，**多发 80 分**（干净复现） |
| 修后（`user_lock`） | 连跑 5 轮，每轮成功 **1** 次、409 7 次 |

回归测试加进 `tests/test_membership.py`「并发原子性」段：8 线程抢签到（断言只成功 1 次、余额只 +20、流水只有一条 checkin），4 个不同用户抢一个单次码（断言只兑走 1 次、`used_count == 1`、只有一位用户 +30）。会员脚本 **56 项全通过**。

**限制（必须知道）**：以上全是**单进程**保证。当前部署就是单 backend 进程，成立；一旦改成多 worker（多进程），签到仍会重复发放，需要换成文件锁（`fcntl`）并在写入前复查当日记录 —— 已写进 `MEMBERSHIP.md` 与排期表 P3。
